# AI Studio — рабочие инструкции для агентов

## Что это за проект

AI-first IDE: основной исполнитель — ИИ-агент, человек ставит задачи и ревьюит изменения. Кроссплатформенно: Android, Linux, Windows. Стек — Kotlin Multiplatform + Compose Multiplatform.

Два компонента с одним протоколом между ними:

- **Workspace Host** — JVM-процесс, владеющий репозиторием и всем исполнением: git, файловая система, LSP, песочница, рантайм агента, реестр инструментов, права, снапшоты, журнал.
- **Клиент** — KMP/Compose, только UI и взаимодействие. Не знает, локальный хост или удалённый; в клиентском коде не должно быть ветвлений по признаку локальности (это проверяется тестом).

Порядок работы: спецификация → задачи с чекбоксами → план реализации → код. Новую функциональность не начинай с кода.

## Принятый процесс

Одна задача плана = один субагент-исполнитель, затем **два независимых ревью**: сначала на соответствие спецификации (сделан ли ровно запрошенный объём, ничего лишнего), потом на качество кода. После правок — повторное ревью. Только потом следующая задача.

Три требования, без которых работа не принимается:

1. **Критерий «Готово когда» подтверждается наблюдаемым фактом**, а не фактом написания кода.
2. **Каждое утверждение о тесте доказывается намеренной поломкой**: сломай проверку → покажи красный вывод → верни → покажи зелёный. Без этого тест считается несуществующим.
3. **Расхождения плана с кодом выносятся в отчёт.** План писался до появления кода и содержит ошибки; сниппеты проверяй, а не копируй.

## Классы дефектов, которые находились в каждой задаче

В пятнадцати задачах подряд находилось от трёх до четырнадцати расхождений плана, и одно-два из них означали, что сниппет **не работает**. Сверяйся с этим списком прежде, чем считать работу готовой.

**API, которого нет.** Проверяй по jar или `javap`, а не по памяти. Уже ловилось: у `org.eclipse.jgit.api.Status` нет `renamed`; у Compose Desktop нет `installDist` (`createDistributable`); Koin `get<Реализация>()` не находит её без `bind`, потому что разрешает по точному ключу типа; `compileCommonMainKotlinMetadata` для набора таргетов только `jvm` + `android` всегда `SKIPPED`; в Ktor 3 `pingPeriodMillis`/`timeoutMillis` вместо `Duration`, `sendClose` заменён на `close(CloseReason)`.

**Тест, который не запускается.** JUnit 5 молча игнорирует `@Test`, возвращающий не-`Unit`: `fun x() = runBlocking { … assertIs<…>() }` не выполняется, а отчёт остаётся зелёным. Пиши тела блочными. И проверяй, что задача теста есть в списке CI: **тест в модуле, не упомянутом в workflow, не существует** — так пропал `:desktopApp:test`, единственное доказательство приёмки этапа.

**Тест, который ничего не проверяет.** Проходит при снятой проверке. Утверждает константу фикстуры вместо результата работы. Сравнивает `StateFlow` вместо `.value`. Ловит `assertFailsWith<Exception>`, то есть что угодно. Проходит по пустоте — нет утверждения, что скан нашёл хотя бы один файл.

**detekt** (правила включены, ослаблять нельзя): `ThrowsCount` ≤ 2 на функцию, `TooManyFunctions` срабатывает уже на **11** внутри класса, `ReturnCount` ≤ 2, `CyclomaticComplexMethod` 15, `MaxLineLength` 120, `SwallowedException`, `NestedBlockDepth`, `UnusedParameter`, `MatchingDeclarationName` (файл с единственной top-level декларацией обязан называться так же).

**`api` против `implementation`.** Тип в публичной сигнатуре → `api`. Нарушалось пять раз; ломает компиляцию у потребителя, а не у автора.

**Пути на Windows.** Сравнивай через `invariantSeparatorsPath`, а не `path`: job `desktop-windows` гоняет `:client-ui:jvmTest` и `:client-state:jvmTest`, и фильтр по `/jvmTest/` сломал бы их.

**Логирование.** `slf4j-api` без провайдера молчит: печатается только предупреждение про NOP. На десктопе нужен `runtimeOnly(libs.slf4j.simple)`, на Android — провайдер только для debug.

**Мёртвый код.** Код «на будущее», не подключённый ни к чему работающему, — это долг, а не готовность. Либо осознанное применение, либо запись в долг, либо удаление.

**`expect class` финален** и не подставляется фейком в `commonTest`. Для тестируемости нужен обычный интерфейс, `expect` — только у фабрики.

**Общее состояние без защиты.** Клиент шлёт запросы из нескольких корутин сразу, и незащищённое общее состояние всплывает не сразу и не локально: `++sequence` терял инкременты (два запроса уходили с одним `RequestId`, хост принимал второй за повтор и отдавал чужой ответ), обычная карта под конкурентными `put` и `remove` теряла ожидающие запросы, `flow.value = flow.value.copy(…)` терял параллельные обновления. Всё, к чему обращается больше одной корутины, — под замок или атомарно (`MutableStateFlow.update`). Нашлось это не в задаче, а на красном CI после закрытия этапа 0: локально набор проходил двенадцать раз подряд и падал только на медленном раннере. Устойчивый CI у нескольких задач сразу — повод искать гонку, а не перезапускать прогон.

**Арифметика тестов в плане почти всегда устарела.** Считай по отчётам `build/test-results/`.

**Конфигурация как источник времени выполнения.** Обращение к `project` в момент выполнения задачи ломает configuration cache; самодельная запись `user_version` в SQLite ломала перезапуск хоста — ведение версии отдавай драйверу.

## Окружение

- **JDK 17 обязателен, по умолчанию в системе JDK 8.** В каждой команде: `export JAVA_HOME=/usr/lib/jvm/java-17-openjdk`. Без этого сборка падает на резолве плагинов.
- Android SDK: `~/Android/Sdk`, путь прописан в `local.properties` (файл не коммитится). Создан AVD `aide-test` (Android 15), KVM работает.
- `10.0.2.2` из эмулятора — псевдоним **loopback машины-хоста**, поэтому хост на `127.0.0.1` эмулятору доступен. Реальному устройству по LAN нужен биндинг на `0.0.0.0` — по умолчанию так не делай.
- `ws://` (cleartext) на Android разрешён только в debug-сборке и только для локальных адресов (`androidApp/src/debug/`). В release запрет по умолчанию — не снимать.
- Каждый вызов shell — новый процесс: `cd` не сохраняется, переменные не переживают вызов. Передавай `cwd` явно или используй абсолютные пути.

## Проверки перед объявлением готовности

```bash
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk

./gradlew :domain:jvmTest :protocol:jvmTest :host-core:test :host-tools:test \
          :host-agent:test :client-state:jvmTest :client-ui:jvmTest :desktopApp:test
./gradlew -p build-logic test
./gradlew detekt
./gradlew verifyModuleBoundaries
./gradlew build
gh run list --limit 3
git status --porcelain
```

Ожидается: тесты зелёные, линт без замечаний, границы модулей соблюдены, `build` успешен, оба job'а CI зелёные, дерево чистое.

`verifyModuleBoundaries` — не формальность. Она запрещает клиентским модулям обращаться к хосту, git и базе напрямую, а домену знать о UI и транспорте. Нарушение — архитектурная ошибка, а не стиль оформления.

**Тест, который не запустился, — красная сборка.** В CI есть шаг, который сравнивает число `@Test` в исходниках модуля с числом `<testcase>` в его отчёте: JUnit молча пропускает `@Test` с не-`Unit` типом возврата, и без такой сверки проверка исчезает, а отчёт остаётся зелёным. Поэтому: не пиши `@Test` в комментариях и KDoc (guard считает по тексту исходников) и, добавляя модуль или новую тестовую конфигурацию, дописывай её и в шаг «Юнит-тесты», и в этот guard.

## Сборка артефактов

Пакеты собираются одной командой на своей платформе: jpackage не умеет кросс-сборку, поэтому `.exe` и `.msi` получаются только на Windows, а `.AppImage`, `.deb` и APK — на Linux.

```bash
./gradlew :androidApp:assembleDebug          # androidApp/build/outputs/apk/debug/*.apk
./gradlew :desktopApp:createDistributable    # каталог с запускаемым приложением (JDK не нужен)
./gradlew :desktopApp:packageDeb             # desktopApp/build/compose/binaries/main/deb/*.deb
tools/appimage.sh                            # desktopApp/build/compose/binaries/main/appimage/*.AppImage
```

`tools/appimage.sh` — не украшение: задача `packageAppImage` у Compose доводит дело только до каталога app-image (jpackage формата AppImage не знает), а файл делает `appimagetool`, который скрипт скачивает сам. Метаданные пакета (`packageName`, `packageVersion`) заданы в `desktopApp/build.gradle.kts` и только латиницей: на Windows jpackage падает на не-ASCII в описании, причём ошибка уходит в файл, которого в логе CI нет — поэтому шаги упаковки печатают `*-err.txt`.

В CI те же пакеты собираются на каждый push и лежат артефактами прогона: `android-apk`, `linux-packages` (`.deb` + `.AppImage`), `windows-exe`, `windows-msi`.

## Git

- Рабочая ветка — ветка текущего этапа. `master` **защищён**: обязательные проверки `build` и `desktop-windows`, прямая отправка проходит только когда проверки на этом коммите уже зелёные.
- Порядок: коммит → `git push origin <рабочая-ветка>` → дождаться зелёного CI (`gh run watch`) → `git branch -f master <sha>` → `git push origin master`.
- Сообщения коммитов — по-русски, в теле объясняй **почему**, а не что. Если коммит исправляет ранее заявленное (в том числе твою ошибку) — скажи это прямо.
- Перед `git add` проверь, что не коммитишь артефакты:
  `git status --porcelain | grep -E '(^|/)(build|\.gradle|\.kotlin)/'` → должно быть пусто.
- Историю не переписывать, чужие ветки не трогать.

## Модули и их границы

| Модуль | Ответственность | Чего не имеет права |
|---|---|---|
| `domain` | модели, инварианты, вычисление риска | UI, транспорт, хост |
| `protocol` | сообщения, кодек, совместимость версий | UI, хост |
| `host-core` | репозиторий, ФС, git, база, очередь ревью, обработчик протокола | клиент (кроме тестов) |
| `host-agent` | прогон агента: цикл, состояния, план, клиент модели, стоимость | клиент, UI, база, `protocol`, `git`, `host-core` (только через порты) |
| `host-tools` | реестр инструментов, права, жёсткие пределы, песочница, журнал | клиент, UI, база, `host-core`, `host-agent`, `protocol`, `git` |
| `client-state` | состояние экранов, соединение, настройки | хост, база |
| `client-ui` | Compose-экраны, ресурсные строки | хост, база |
| `platform-*` | платформенное связывание точки входа | — |
| `build-logic` | конвенции сборки, правило границ модулей | — |

Зависимость объявляется там, где тип **импортируется напрямую**; транзитивный `api` — не замена.

## Чего не делать

- Не считать задачу выполненной по факту написания кода — только по критерию.
- Не менять спецификацию под код и не ослаблять критерии приёмки задним числом. Если требование невыполнимо — скажи об этом, решение принимает владелец.
- Не подключать код «на будущее» ради видимости готовности.
- Не молчать о непроверенном: в отчёте обязателен раздел «что осталось непроверенным».
- Не считать, что раз CI зелёный, то всё проверено: CI проверяет ровно те задачи, что перечислены в workflow.
