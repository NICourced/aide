# AI Studio (Agent IDE) — спецификация

| Поле | Значение |
|---|---|
| Версия | 0.1 (черновик) |
| Дата | 2026-09-22 |
| Статус | на ревью |
| Платформы | Android, Linux, Windows (перспектива: iOS, macOS) |
| Устройства | смартфоны 6–7″, планшеты, десктопы |
| Задачи | `docs/tasks/` (индекс и легенда — `docs/tasks/README.md`) |

Обозначения требований: `FR-<ГРУППА>-<N>` — функциональное требование, `NFR-<N>` — нефункциональное. Каждое требование имеет ID, чтобы на него ссылались задачи и тесты.

---

## 1. Обзор

### 1.1. Суть продукта

Кроссплатформенная среда разработки, в которой основным исполнителем является ИИ-агент, а человек выступает постановщиком задач и ревьюером. Разработка ведётся не написанием кода, а управлением агентом, ревью его изменений и точечным вмешательством.

**Ключевая метафора:** «пульт управления ИИ-разработкой + инбокс ревью изменений», а не мобильная версия VS Code.

### 1.2. Что это значит на практике

Основной цикл работы (далее — **review-цикл**):

1. Пользователь формулирует задачу текстом или голосом.
2. Агент показывает план, получает подтверждение по правилам режима автономности.
3. Агент работает, пользователь видит лог вызовов инструментов, время и стоимость.
4. Агент оформляет результат как пакет изменений и ставит его в инбокс ревью.
5. Пользователь принимает, отклоняет или возвращает на доработку — по блокам или пакетом.
6. Каждое принятие и откат обратимо через снапшоты.

Всё, что не обслуживает этот цикл, — вторично.

### 1.3. Антипаттерн продукта

Приложение, где первым экраном открывается файловое дерево, а diff показывается как сырой unified diff. Это явно исключено (см. § 2.2).

## 2. Цели, антицели, метрики

### 2.1. Цели

| ID | Цель | Проверяемый признак |
|---|---|---|
| G1 | Разработка возможна и удобна с мобильного устройства | пользователь закрывает задачу «от постановки до принятия» на телефоне, не открывая десктоп |
| G2 | У агента полноценные инструменты для автономной работы | агент может читать/править файлы, запускать тесты и линтер, коммитить, вызывать API — без ручных операций пользователя |
| G3 | Прозрачный контроль над действиями агента | до начала работы виден план; во время — лог каждого вызова инструмента с результатом; доступны пауза, стоп, откат |
| G4 | Удобное ревью изменений на маленьком экране | ревью пакета из 40 блоков выполняется без горизонтального скролла и без side-by-side |
| G5 | Единый опыт на Android, Linux, Windows, а после этапа 8 — также на iOS и macOS | один и тот же review-цикл, одинаковые жесты и раскладка, различия только в платформенных мелочах |
| G6 | Максимальная скорость и надёжность | метрики § 11 выдерживаются, данные не теряются при сбоях и сворачивании приложения |

### 2.2. Антицели

| ID | Антицель | Как обеспечивается |
|---|---|---|
| NG1 | Не заменяет десктопную IDE для профессиональной разработки с клавиатурой | не конкурируем по функциям редактора (рефакторинги уровня десктопной IDE: extract, change signature целиком; отладчик, мультикурсор); быстрые действия уровня hunk'а и символа (FR-EDITOR-20) в запрет не входят; редактор вторичен |
| NG2 | Редактор кода — не основной экран | редактор не имеет постоянной вкладки, открывается поверх и закрывается жестом |
| NG3 | Пользователь не печатает много кода на телефоне | приоритет правок через ИИ; ручной ввод — точечный |
| NG4 | Сырой unified diff не показывается | hunk-first карточки (§ 5.2) |
| NG5 | Нет side-by-side diff на узких экранах | режим «до/после» с переключением |
| NG6 | Действия агента не скрываются | лог вызовов инструментов неотключаемый; стоимость и время видны |
| NG7 | У агента нет неограниченного доступа | модель прав § 10.1; по умолчанию запись и исполнение требуют подтверждения |

### 2.3. Метрики продукта (для оценки после запуска)

- Доля задач, закрытых полностью с мобильного устройства.
- Доля пакетов изменений, принятых без правок человеком.
- Медиана времени от постановки задачи до принятия пакета.
- Доля откатов к снапшотам (индикатор непредсказуемости агента).
- Число подтверждений на одну задачу (индикатор доверия к режиму автономности).

## 3. Модель исполнения и топология

Это главный архитектурный раздел: от него зависят все остальные.

### 3.1. Компоненты

| Компонент | Ответственность |
|---|---|
| **Workspace Host** | владеет репозиторием и всем исполнением: git, файловая система, индексация, LSP, песочница (терминал, тесты, линтер, браузер, БД), рантайм агента, реестр tools, права, снапшоты, аудит |
| **Клиент** | UI и взаимодействие: Review Inbox, diff, чат, редактор-лупа, панели кнопок, голосовой ввод. Не исполняет код и не хранит состояние репозитория |

Клиент общается с хостом по одному протоколу (§ 8.4) и не знает, локальный хост или удалённый.

### 3.2. Что где выполняется

| Работа | Где выполняется | Обоснование |
|---|---|---|
| git-операции, ветки, снапшоты | хост | единая точка правды для истории |
| чтение/запись файлов | хост | клиент никогда не пишет в ФС репозитория напрямую |
| запуск агента и LLM-вызовы | хост | ключи и стоимость в одном месте; телефон не тратит батарею на сеть к провайдеру |
| тесты, линтер, сборка, терминал | хост | телефон не тянет тяжёлые стеки |
| LSP, индексация, поиск по проекту | хост, рядом с воркспейсом | индекс требует памяти; сервер и клиент не должны расходиться |
| парсинг diff, разбиение на блоки | хост формирует, клиент рендерит | структура одна для всех платформ |
| рендер UI, жесты, хаптик | клиент | нативное поведение платформы |
| кэш просмотренного кода и diff | клиент (локально) | офлайн-просмотр без сети |

### 3.3. Режимы развёртывания

| Режим | Как выглядит | Когда используется |
|---|---|---|
| **Локальный** | хост и клиент на одной машине; хост — тот же процесс или сайдкар | десктоп Linux/Windows, работа офлайн |
| **Удалённый** | хост на другом устройстве или в контейнере; клиент подключается по сети | телефон без мощностей; тяжёлые стеки; общий сборочный сервер |

Оба режима реализуют один протокол. Переключение режима не меняет UI и не требует пересборки.

Транспорт удалённого подключения (relay-сервис / VPN-меш / SSH-туннель) выбирается на этапе 5; требование к любому варианту: сквозное шифрование и аутентификация по ключу устройства, без пароля в открытом виде.

### 3.4. Границы ответственности

- Клиент не имеет доступа к секретам, файлам и git напрямую — только через API хоста.
- Хост не рендерит UI и не хранит UI-состояние; сессию ревью можно продолжить на другом устройстве.
- Хост не решает, что показать; он отдаёт структурированные данные (`ChangePacket`, `Hunk`, `FileChange`), а клиент выбирает представление под ширину экрана.

### 3.5. Офлайн-поведение

- Просмотр ранее загруженных файлов, diff и пакетов — без сети (`NFR-7`).
- Решения ревью (принять/отклонить), принятые офлайн, ставятся в очередь и применяются при восстановлении связи.
- Работа агента офлайн невозможна; UI явно показывает состояние «нет связи, показаны кэшированные данные» и не притворяется, что всё в порядке.
- Очередь офлайн-действий относится только к решениям ревью: выдача и отзыв разрешений на tools офлайн в очередь не ставятся — для них нужно соединение с хостом.

## 4. Домен и понятия

| Понятие | Определение |
|---|---|
| **Task** | постановка от пользователя: текст или голос + опциональные файлы/ссылки. Имеет статус, ветку, историю прогонов агента |
| **AgentRun** | один прогон агента по задаче: план, шаги, вызовы инструментов, стоимость, время, результат |
| **ToolCall** | один вызов инструмента агентом: имя, аргументы, результат, длительность, стоимость, признак подтверждения |
| **ChangePacket** | пакет изменений — единица ревью, соответствует одной задаче. Содержит список `FileChange`, оценку риска, статус тестов, объяснение агента |
| **FileChange** | изменения одного файла в пакете: тип (добавлен/изменён/удалён/переименован), число добавленных и удалённых строк, список `Hunk` |
| **Hunk** | один связанный блок изменений — единица показа и решения на мобильном экране |
| **RiskLevel** | оценка риска пакета и отдельного hunk: `safe` / `normal` / `risky` (§ 5.1.4) |
| **Snapshot** | состояние репозитория, к которому можно откатиться, до или после действия агента / ручной правки |
| **AutonomyMode** | режим автономности агента (§ 5.3.1) |
| **ToolPermission** | правило доступа агента к инструменту: `allow` (без спроса) / `ask` (с подтверждением) / `deny` |
| **ReviewDecision** | решение по hunk или пакету: `accepted` / `rejected` / `changes_requested` |

### 4.1. Инварианты

1. Каждый `Hunk` принадлежит ровно одному `FileChange`, каждый `FileChange` — ровно одному `ChangePacket`.
2. Пакет неизменяем после попадания в инбокс. Доработка создаёт новую ревизию пакета, старая остаётся в истории.
3. Любое изменение в репозитории (агентом или человеком) имеет снапшот до и после.
4. Каждое принятое изменение имеет автора в истории git: агент либо человек.
5. `RiskLevel` пакета не может быть ниже максимального `RiskLevel` его hunk'ов.
6. Решения ревью не теряются: если пакет был частично принят и пользователь закрыл приложение, состояние восстанавливается.

## 5. Функциональные требования

### 5.1. Review Inbox (`FR-INBOX`)

Центральный экран приложения — очередь изменений, сделанных агентом. Не файловое дерево и не редактор.

| ID | Требование |
|---|---|
| FR-INBOX-1 | Инбокс — экран по умолчанию при запуске, если есть непроверенные пакеты |
| FR-INBOX-2 | Одна карточка = один `ChangePacket` = один смысловой пакет изменений (задача) |
| FR-INBOX-3 | Карточка показывает: название задачи, список файлов, число добавленных и удалённых строк, `RiskLevel`, статус тестов, краткое объяснение от агента |
| FR-INBOX-4 | Карточка показывает источник: «Агент» или «Вы» |
| FR-INBOX-5 | Карточка показывает статус: ожидает ревью / в работе / принято / отклонено |
| FR-INBOX-6 | Фильтры: безопасные, рискованные, конфликты, падающие тесты |
| FR-INBOX-7 | Группировка по смыслу: Авторизация, Сетевой слой, Тесты, Рефакторинг и т. п. — по классификации агента, с возможностью переопределить вручную |
| FR-INBOX-8 | Группировка по источнику и по статусу |
| FR-INBOX-9 | Действия на карточке: «Показать diff», «Спросить агента», «Принять всё безопасное» |
| FR-INBOX-10 | «Принять всё безопасное» применяет только hunk'и с `RiskLevel = safe` и зелёными тестами; остальное остаётся в инбоксе |
| FR-INBOX-11 | Конфликты (расхождение с изменениями пользователя или другого пакета) выделяются явно и не могут быть приняты пакетно |
| FR-INBOX-12 | Падающие тесты блокируют пакетное принятие и требуют явного подтверждения при принятии отдельного hunk'а |
| FR-INBOX-13 | Пакет можно вернуть на доработку с комментарием; агент получает комментарий как контекст |
| FR-INBOX-14 | Инбокс доступен офлайн по кэшу, решения ставятся в очередь (§ 3.5) |

### 5.2. Мобильный diff (`FR-DIFF`)

#### 5.2.1. Принцип hunk-first

| ID | Требование |
|---|---|
| FR-DIFF-1 | Один изменённый блок — одна карточка на экране. Основная единица навигации — hunk, не файл |
| FR-DIFF-2 | Вертикальный свайп переключает hunk'и |
| FR-DIFF-3 | Сверху карточки: имя файла и номер строки |
| FR-DIFF-4 | Снизу карточки: объяснение агента — что изменено, зачем, риски, статус тестов |
| FR-DIFF-5 | Сырой unified diff не показывается никогда |
| FR-DIFF-6 | Side-by-side не используется ни на одной ширине экрана |

#### 5.2.2. Визуализация

| ID | Требование |
|---|---|
| FR-DIFF-7 | Тонкая цветовая полоса слева: зелёная — добавление, красная — удаление |
| FR-DIFF-8 | Подсветка на уровне слов, а не только строк |
| FR-DIFF-9 | Длинные строки переносятся; горизонтального скролла нет ни в одном состоянии |
| FR-DIFF-10 | Неизменённый контекст свёрнут с указанием объёма: «... 14 строк ...». Раскрывается тапом |
| FR-DIFF-11 | Мини-карта изменений справа: точки по числу hunk'ов, тап — переход, текущий hunk выделен |
| FR-DIFF-12 | Режим «до/после» переключателем на одном и том же месте, без side-by-side |
| FR-DIFF-13 | Внутри hunk'а доступен показ только изменённых слов — режим «только суть» |

#### 5.2.3. Семантический diff

| ID | Требование |
|---|---|
| FR-DIFF-14 | Для каждого hunk'а агент даёт объяснение: что изменено и почему |
| FR-DIFF-15 | Указываются риски: затронут публичный API, изменена схема БД, изменено поведение по умолчанию, затронуты права доступа |
| FR-DIFF-16 | Указываются связи: «связано с `api_client.dart`, `auth_service.dart`» — по графу импортов и по истории правок |
| FR-DIFF-17 | Показываются результаты тестов и линтера, относящиеся к hunk'у, а не только к пакету |
| FR-DIFF-18 | Объяснение хранится вместе с пакетом и не пересчитывается при каждом открытии |

Границы этапа: AST-aware (структурный) diff, который сопоставляет изменения по узлам синтаксического дерева, в MVP не реализуется. В MVP — построчный diff с разбиением на hunk'и + объяснение от LLM + связи по графу импортов. AST-diff — этап 7.

### 5.3. Управление агентом (`FR-AGENT`)

#### 5.3.1. Режимы автономности

| ID | Требование |
|---|---|
| FR-AGENT-1 | «Только предлагать» — агент не применяет ничего сам; результат только в инбоксе как предложение |
| FR-AGENT-2 | «Спрашивать перед изменениями» — каждое действие, изменяющее репозиторий или исполняющее код, требует подтверждения |
| FR-AGENT-3 | «Авто-применять безопасное» — изменения уровня `safe` применяются автоматически, остальные идут в инбокс |
| FR-AGENT-4 | «Полный автомат с чекпоинтами» — агент работает без подтверждений, но перед каждым шагом ставит снапшот |
| FR-AGENT-5 | Режим переключается в любой момент и не влияет на уже начатый `AgentRun` без явного согласия |
| FR-AGENT-6 | Определение «безопасного» фиксировано явным списком (§ 5.3.2) и видно пользователю в интерфейсе |

#### 5.3.2. Классификация риска

`safe` — все условия выполнены:

- изменения только в тестах, документации, файлах локализации или результатах форматтера;
- тесты и линтер зелёные;
- объём ниже настроенного порога (по умолчанию 50 строк на пакет);
- не затронуты публичный API, схема БД, конфигурация прав и секреты;
- не удалены файлы.

`risky` — хотя бы одно: удалены файлы, затронуты публичный API, схема БД, права доступа или секреты, тесты красные, объём выше порога в 5 раз.

`normal` — всё остальное.

`RiskLevel` вычисляется детерминированно по правилам выше; LLM может добавить пояснение, но не может понизить уровень.

#### 5.3.3. Прозрачность работы

| ID | Требование |
|---|---|
| FR-AGENT-7 | План показывается до начала работы и требует подтверждения по правилам текущего режима |
| FR-AGENT-8 | Лог вызовов инструментов доступен всегда: чтение файла, запись, запуск тестов, вызов API, коммит |
| FR-AGENT-9 | Каждая запись лога содержит: инструмент, аргументы, результат, длительность, стоимость, был ли это шаг с подтверждением |
| FR-AGENT-10 | Показываются суммарное время и стоимость прогона, а также стоимость по текущей задаче |
| FR-AGENT-11 | Доступны пауза и стоп в любой момент `AgentRun`; стоп обратим до последнего снапшота |
| FR-AGENT-12 | Доступен откат к предыдущему снапшоту с предпросмотром того, что будет отменено |
| FR-AGENT-13 | Лог вызовов инструментов нельзя отключить — это требование прозрачности, а не настройка |

#### 5.3.4. Мультиагентность

| ID | Требование |
|---|---|
| FR-AGENT-14 | Роль «Основной агент» — пишет код |
| FR-AGENT-15 | Роль «Ревьюер» — проверяет изменения основного агента и оставляет замечания |
| FR-AGENT-16 | Роль «Тестировщик» — запускает тесты и интерпретирует результаты |
| FR-AGENT-17 | Роль «Объяснитель» — комментирует изменения для ревью |
| FR-AGENT-18 | Роли включаются по отдельности; каждая имеет свою стоимость, видимую пользователю |
| FR-AGENT-19 | Конфликт между ролями (ревьюер не согласен с основным агентом) показывается пользователю как решение, а не разрешается автоматически |

### 5.9. Стоимость и лимиты (`FR-COST`)

Единая модель, на которую ссылаются все требования про деньги. Одна цена, три уровня суммирования, три лимита с разным поведением.

**Стоимость**

- Цена вызова задаётся у инструмента: явная ставка либо ноль для бесплатных.
- Стоимость прогона — сумма стоимостей его вызовов. Стоимость задачи — сумма стоимостей всех её прогонов.
- Если цена вызова неизвестна, стоимость помечается как «неизвестна» и не считается нулём; итог по задаче с такой позицией помечается как неполный.

**Лимиты**

| Лимит | Уровень | Поведение при достижении |
|---|---|---|
| Мягкий лимит роли | роль внутри прогона | на 80 % — предупреждение; при достижении роль останавливается между вызовами, прогон продолжается |
| Жёсткий лимит прогона | прогон | прогон останавливается между вызовами с сообщением о причине |
| Жёсткий лимит задачи | задача | новый прогон по задаче не запускается; текущий доводится до ближайшего безопасного шага и останавливается |

| ID | Требование |
|---|---|
| FR-COST-1 | У инструмента есть цена вызова: явная ставка либо ноль для бесплатных |
| FR-COST-2 | Стоимость считается на трёх уровнях — вызов, прогон, задача — и совпадает с суммой записей журнала |
| FR-COST-3 | Задаются три лимита: мягкий на роль, жёсткий на прогон, жёсткий на задачу |
| FR-COST-4 | Достижение лимита останавливает работу, но никогда не откатывает уже выполненные вызовы |
| FR-COST-5 | Неизвестная цена помечается как «неизвестна»; итог с такой позицией помечается как неполный |
| FR-COST-6 | Достигнутый лимит снимается или поднимается пользователем, после чего работа продолжается с того же места |

## 6. UX-контракты

### 6.1. Состояния экранов

Каждый экран обязан иметь определённые состояния; отсутствие любого из них считается незавершённостью:

| Состояние | Что показывается |
|---|---|
| пусто | почему пусто и что сделать: «Нет изменений на ревью. Поставьте задачу агенту» |
| загрузка | скелетон структуры, а не пустой экран и не бесконечный спиннер |
| ошибка | что случилось, что можно сделать, кнопка повтора; техническая деталь — по запросу |
| нет связи | работа с кэшем + явная пометка + очередь действий (§ 3.5) |
| нет прав | какой tool или действие требуют разрешения и как его выдать |

### 6.2. Навигация

- Назад всегда возвращает в тот контекст, из которого пользователь пришёл (hunk → файл → пакет → инбокс).
- Системный жест «назад» на Android работает как кнопка «Назад» и не выходит из приложения, если есть куда вернуться внутри навигации.
- Редактор и bottom sheet закрываются одним жестом, без подтверждения, если нет несохранённых правок.

### 6.3. Подтверждения

- Подтверждение требуется только там, где действие необратимо или выходит за пределы воркспейса.
- Подтверждения не дублируются: если действие уже разрешено в режиме автономности, второй раз не спрашиваем.
- Текст подтверждения содержит, что именно произойдёт и как откатить.

### 6.4. Обратная связь

- Долгая операция показывает прогресс и позволяет продолжить работу в другом месте приложения.
- Действие, применение которого занимает больше 300 мс, показывает промежуточное состояние, а не «замирает».
- Ошибка агента не выглядит как ошибка приложения: пользователь понимает, что не получилось у агента.

## 7. Технологический стек

### 7.1. Выбранный стек

| Слой | Технология |
|---|---|
| Общая логика | Kotlin Multiplatform (KMP) |
| UI | Compose Multiplatform (Android, Desktop) |
| Платформенный UI при необходимости | Jetpack Compose (Android), SwiftUI (iOS) |
| Десктоп | Compose for Desktop (JVM) |
| Тяжёлые вычисления (опционально) | Rust-модули через FFI: парсинг, AST, индексация, git |
| Хост | JVM-сервис на Kotlin; в удалённом режиме — тот же сервис в контейнере |

### 7.2. Обоснование

- Нативная компиляция для Android, JVM для десктопа.
- Единая логика для всех платформ — один review-цикл везде.
- Compose Multiplatform стабилен для Android и Desktop с 2025 года, активно поддерживается JetBrains и Google.
- Возможность постепенно переписать критичные экраны на нативные API, не переписывая логику.

### 7.3. Рассмотренные альтернативы

| Вариант | Почему не выбран |
|---|---|
| Flutter (Dart) | единая кодовая база и высокая скорость разработки, но менее нативный вид и больший расход памяти |
| Tauri (Rust + WebView) | лёгкий десктоп, но мобильная поддержка незрелая |
| Avalonia (.NET) | мощный десктоп, слабая мобильная поддержка |
| .NET MAUI | не поддерживает Linux — не подходит |
| React Native | подходит только при сильной команде JS/TS и невысоких требованиях к производительности |

Отказ от WebAssembly как способа запускать LSP и тяжёлые языки: зрелость инструментов недостаточна, а второй механизм исполнения удваивает объём работ. Тяжёлые языки закрываются удалённым хостом (§ 3.3).

## 8. Архитектура

### 8.1. Слои

| Слой | Содержание | Разрешённые зависимости |
|---|---|---|
| UI | Compose Multiplatform, платформенные вставки | логика (только через интерфейсы сценариев) |
| Логика (KMP) | проекты, git, diff, управление агентом, реестр tools, очередь ревью | доменные модели, клиент протокола |
| Протокол | клиент хоста: типы сообщений, сериализация, реконнект | доменные модели |
| Хост | исполнение: git, ФС, LSP, песочница, агент, права, снапшоты, аудит | доменные модели, интеграции |
| Вычислительный (Rust, опционально) | парсинг, AST, индексация, git-операции | вызывается из хоста через FFI |
| Интеграции | LSP, Git, HTTP/GraphQL/gRPC, MCP-клиенты | внешние системы |

Правило: UI не знает о хосте больше, чем описано протоколом. Домен не знает ни о UI, ни о транспорте.

### 8.2. Модули

| Модуль | Ответственность | Ключевой вопрос, на который отвечает |
|---|---|---|
| `domain` | модели и правила: `ChangePacket`, `Hunk`, `RiskLevel`, режимы автономности | что это за данные и какие у них инварианты |
| `protocol` | сообщения клиент↔хост, сериализация, версионирование | как клиент и хост договариваются |
| `host-core` | репозиторий, ветки, снапшоты, очередь ревью | как меняется состояние репозитория |
| `host-agent` | прогон агента, план, шаги, роли | как агент выполняет задачу |
| `host-tools` | реестр tools, права, секреты, песочница, аудит | что агенту разрешено и что он вызвал |
| `host-lsp` | LSP-клиент, индексация, поиск | где определение символа и кто его использует |
| `client-ui` | экраны и компоненты Compose | как это выглядит и на что нажимается |
| `client-state` | состояние экранов, очередь действий, кэш | что показать прямо сейчас |
| `platform-*` | expect/actual: хранилище секретов, хаптик, файловые диалоги, сеть | как ведёт себя конкретная платформа |
| `rust-bridge` | FFI к Rust-модулям | как вызвать тяжёлое вычисление |

### 8.3. Ключевые технические решения

| Решение | Как реализуется |
|---|---|
| Каждое изменение агента — отдельный коммит | задача = ветка `ai/<task-id>`; каждый шаг агента = коммит в ней; принятие пакета = мерж ветки |
| Снапшоты | скрытые refs `refs/ai/snap/<timestamp>-<label>`; создаются до и после каждой правки агента и каждой ручной правки; хранятся N последних (по умолчанию 50 либо по настройке) |
| Разделение правок агента и человека | ручные правки коммитятся в текущую ветку с автором-человеком; агент — в свою ветку; при конфликте — явный конфликт, а не тихое слияние |
| LSP | живёт там же, где воркспейс; клиент общается с ним через хост, не напрямую |
| Совместное редактирование человеком и агентом | блокировка файла на время правки; CRDT не используется (см. этап 7) |
| Офлайн | локальный кэш файлов, diff и пакетов на клиенте; очередь решений ревью |
| Семантический diff | в MVP — hunk'и + объяснение LLM + связи по графу импортов; AST-aware — этап 7 |
| Хранение метаданных | локальная БД на хосте (SQLite): задачи, прогоны, вызовы инструментов, решения ревью, права. Код в git, не в БД |

### 8.4. Протокол клиент ↔ хост

- Транспорт: WebSocket с бинарной сериализацией; поверх — HTTP для загрузки больших файлов и артефактов.
- Протокол версионируется; несовпадение версий — явная ошибка с предложением обновить, а не частично работающий UI.
- Поддерживается реконнект с продолжением сессии: клиент получает состояние на момент отключения, а не начинает заново.
- Все изменяющие операции идемпотентны по идентификатору запроса: повтор после обрыва связи не создаёт вторую правку.

### 8.5. Тестируемость

- Логика хоста тестируется без UI и без сети.
- Разбиение diff на hunk'и и вычисление `RiskLevel` — чистые функции с фиксированными входами и выходами.
- Протокол тестируется на совместимость версий.
- UI-тесты — на критичный review-цикл и режимы управления.

## 9. Данные и хранение

| Данные | Где хранятся | Срок жизни |
|---|---|---|
| Код репозитория | git на хосте | постоянно |
| Ветки задач | git, `ai/<task-id>` | до мержа или удаления задачи |
| Снапшоты | git, `refs/ai/snap/*` | последние 50 либо по настройке |
| Индекс поиска (файлы и символы) | каталог данных хоста, вне рабочей копии репозитория | до смены версии формата |
| Задачи, прогоны, вызовы инструментов, решения ревью (включая платформу клиента, принявшего решение) | SQLite на хосте | до удаления задачи |
| Секреты, токены | защищённое хранилище платформы (Android Keystore, libsecret, DPAPI, macOS Keychain) | до отзыва |
| Кэш просмотра для офлайна, черновики правок и очередь офлайн-решений | локально на клиенте | вытесняется по размеру |
| Настройки, раскладка панелей, режим управления | локально на клиенте, синхронизируются между устройствами | постоянно |

Правила:

1. Секреты никогда не попадают в git, снапшоты, логи и в текст промптов.
2. Состояние ревью привязано к ревизии пакета: если пакет изменился, прежние решения не применяются автоматически.
3. Удаление задачи не удаляет снапшоты, к которым она откатывалась, пока их не вытеснит лимит.

## 10. Безопасность, права, откат

### 10.1. Модель прав

- Права описываются как возможности: чтение ФС внутри воркспейса, запись ФС внутри воркспейса, запуск команд, сеть, доступ к секрету, git-операции.
- Внешние вызовы и запись за пределами воркспейса запрещены всегда — это не настраивается.
- Каждый tool имеет разрешение `allow` / `ask` / `deny`, отдельно для чтения и записи (FR-TOOLS-8).
- Разрешение выдаётся на один вызов, на сессию или постоянно; выданное на один вызов не запоминается.
- Требование NG7: по умолчанию запись и исполнение — `ask`.

### 10.2. Аудит действий агента

- Каждый `ToolCall` записывается: инструмент, аргументы, результат, длительность, стоимость, был ли подтверждён человеком.
- Журнал аудита неизменяем средствами приложения и экспортируется пользователем.
- Удаление задачи не удаляет журнал её прогонов до истечения срока хранения (по умолчанию 90 дней).

### 10.3. Откат и восстановление

| ID | Требование |
|---|---|
| NFR-SAFE-1 | Undo/redo на уровне файла и на уровне проекта |
| NFR-SAFE-2 | Снапшот создаётся до и после каждой ручной правки и каждого действия агента, изменяющего репозиторий |
| NFR-SAFE-3 | Откат доступен как для правок агента, так и для собственных правок |
| NFR-SAFE-4 | Если применяемое изменение ломает тесты, пользователь получает предупреждение до применения, с указанием упавших тестов |
| NFR-SAFE-5 | Откат не удаляет историю: он оформляется как обратный коммит, а не как перезапись |
| NFR-SAFE-6 | При падении хоста во время прогона состояние репозитория восстанавливается к последнему снапшоту при запуске |

## 13. Риски и открытые вопросы

### 13.1. Риски

| Риск | Влияние | Снижение |
|---|---|---|
| Производительность на мобильных: тяжёлые языки, большие репозитории | цель G1 не достигается | вычисления на хосте (§ 3.2); индексация инкрементальная; этап 6 |
| Сложность diff: семантический diff требует парсеров под много языков | сроки | в MVP — hunk'и и объяснение LLM; AST — этап 7, по языкам приоритетно |
| Автономность агента: нежелательные изменения | потеря доверия и данных | правила риска (§ 5.3.2), снапшоты, права § 10.1 |
| Зрелость Compose Multiplatform на десктопе | экосистема компонентов ещё развивается | платформенные вставки там, где нужно; не изобретать тяжёлые виджеты |
| Мультиагентность: координация и конфликты между агентами | непредсказуемость | сначала детерминированные проверки, затем LLM-роли; конфликт ролей выносится пользователю |
| Кроссплатформенность UI: различия в жестах, клавиатурах, экранах | расхождение опыта | режимы управления (§ 5.5.1) как единый слой совместимости |
| Стоимость LLM-прогонов | расходы пользователя | стоимость видна до и во время прогона; лимиты на задачу |
